**Remediation Hooks** allow Wardress to take active measures when a defacement is detected, rather than just sending an alert. 

You can configure an outbound webhook URL that Wardress will POST an incident payload to. This allows you to integrate Wardress with serverless functions, CI/CD pipelines, or edge proxies to automatically isolate the affected system.

## Supported Action Types

While Wardress simply POSTs the payload to the URL you provide, you must assign an **Action Type** label to the hook to drive UI clarity:
- `git_rollback`: Rollback the deployment via a CI provider.
- `docker_restart`: Restart the container via a Portainer webhook.
- `maintenance_page_swap`: Swap the load balancer to a static maintenance page.
- `custom_webhook`: Generic payload delivery.

## Execution Lifecycle

Because automated infrastructure changes are highly destructive (and a false positive could accidentally take a healthy site offline), Wardress implements a strict **Fail-Safe** confirmation queue by default.

<Steps>
  <Step title="Pending Confirm">
    When a flagged scan's risk score meets or exceeds the **hook's own `trigger_threshold`**, an execution row is created in the `pending_confirm` state. It will **not execute**. Each `(hook, scan)` pair is unique, so an alert redelivery never double-fires a hook.
  </Step>
  <Step title="Operator Approval">
    An operator (Admin or Analyst) must log into the dashboard to explicitly approve the pending remediation (or call the REST confirm endpoint directly with suitable credentials). There is no Telegram approval path — the Telegram Bot's Confirm/Cancel buttons apply to AI-assistant actions only, never to remediations.
  </Step>
  <Step title="Queued">
    Once confirmed, the hook transitions to `queued` and is dispatched to a Celery worker.
  </Step>
  <Step title="Succeeded / Failed">
    A **separate** Celery task (never the scan body) executes the HTTP POST with a 20-second timeout. A non-2xx or unreachable destination transitions the row to `failed` with a user-safe detail. The webhook URL is never echoed into that detail because it may embed a credential — and a broken hook *never* affects scanning.
  </Step>
</Steps>

## Auto-Execute (Opt-In)

If you are absolutely confident in your suppression rules and wish to achieve zero-minute response times, an Admin can enable auto-execute for a hook.

The dashboard's **Add hook** dialog exposes this choice at creation time. There is no edit form in the dashboard — after a hook exists, the panel offers only Enable/Disable and Delete. To change `requires_manual_confirm` (or any other field) on an existing hook, call the REST endpoint directly as an Admin:

```bash
curl -X PATCH -H "Authorization: Bearer <admin-session-token>" \
  -H "Content-Type: application/json" \
  -d '{"requires_manual_confirm": false}' \
  http://localhost:8321/api/sites/<site_id>/remediation-hooks/<hook_id>
```

When `requires_manual_confirm` is disabled, flagged scans skip the `pending_confirm` state entirely and immediately enter the `queued` state for execution. As an additional brake, an auto-executing hook that fired recently is held in the confirmation queue instead of firing again until its cooldown expires.

<Caution>
  Only disable `requires_manual_confirm` if you have thoroughly tested your baseline and suppression rules. Auto-executing a rollback on a false positive will cause an unnecessary outage.
</Caution>

## Security

Webhook URLs routinely contain embedded secrets (like API tokens in query parameters: `?token=abc1234`). For this reason, all webhook URLs are **Fernet-encrypted** at rest in the PostgreSQL database.

Hook URLs also go through the same outbound-fetch discipline as every other URL Wardress fetches:

- **Save-time validation.** A hook's URL must be an `http(s)` URL that an HTTP client can actually construct a request for (a malformed port or control characters are rejected with a validation error), and its host must pass the SSRF address gate: loopback, private (RFC1918), link-local, and cloud-metadata targets are refused by default.
- **Internal receivers are opt-in.** If your receiver genuinely lives on the internal network, set `allow_private_networks: true` on the hook (an admin-only field on create/update; also surfaced in the hook response). This mirrors the per-site flag for monitored targets.
- **Pinned fires.** When a hook fires, the worker resolves the host once and pins the connection to the resolved address through the same transport used for site probes — so DNS cannot silently change between validation and delivery — and honors the hook's stored opt-in.
