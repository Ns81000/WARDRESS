## Authentication & Access

Access the Wardress dashboard by navigating to `http://localhost:8321` (or your configured URL) in your web browser. 

<Frame>
  <img src="/screenshots/login.png" alt="Authentication Screen" />
</Frame>

Log in using the email and password generated during the installation process. The portal enforces session durations, server-side rate limits, and a per-account lockout with escalating delays after repeated failures — failed attempts are recorded in the audit trail — to prevent brute-force attacks.

## Main Dashboard (Sites)

Upon logging in, you are greeted by the Main Site Directory. This is your central operations deck.

<Frame>
  <img src="/screenshots/sites.png" alt="Sites Dashboard" />

From this view, you can:
- View all configured sites and their current status (e.g., Healthy, Flagged, Scanning).
- See active alerts at a glance.
- Trigger immediate manual scans using the quick-action run keys.

## Managing a Site

Clicking on any site in the dashboard opens the **Site Detail Panel**.

<Frame>
  <img src="/screenshots/site-detail.png" alt="Site Detail" />
</Frame>

Here, operators can:
- **Manage Baselines**: View when the last baseline was captured, or force a re-baseline to update the trusted state.
- **Schedule Scanning Intervals**: Adjust the base interval for automated periodic scans. Note that Wardress utilizes *Adaptive Cadence Scanning*, tightening the interval dynamically if suspicious activity is detected.
- **Define Thresholds**: Configure the sensitivity and risk score thresholds required to trigger an alert.
- **Add Suppression Rules**: Define regex patterns to ignore specific dynamic elements on the page.

### Capture Failures & Bot Protection

Baseline and scan captures run a stealth-hardened headless browser. When a capture lands on a bot-protection challenge page (such as a Cloudflare challenge), Wardress waits for the challenge to auto-solve for a real browser and then re-checks the page. If the page is still challenged, the capture is retried once with a longer wait before it finally fails with a clear error — *Site is behind bot protection that could not be bypassed (Cloudflare challenge detected)* — and the baseline or scan is marked **Failed**. Challenge pages are never stored as site content, so a blocked capture can never poison comparisons or trigger false change alerts.

Temporary network problems do not fail a capture outright: if a page's navigation times out or fails at the network level, Wardress pauses briefly and tries the capture once more with a shorter navigation window, and each retry re-runs the full preparation (consent cookies, banner dismissal, scrolling) on a fresh browser. Refusals by the site-security policy (internal or private network targets) and permanent failures are never retried — a second attempt could not change their outcome. The number of retries that preceded a capture is recorded in the capture evidence stored with the scan, and every retry decision is written to the worker log with its reason.

<Info>
  If a monitored site sits behind persistent bot protection, work with the site owner to allow-list your instance, or use the site's *allow private networks* setting only for genuinely internal targets. A failed capture is always visible on the site detail panel with the reason above.
</Info>

### Scrolling & Lazy Content

Before a baseline or scan is stored, Wardress auto-scrolls the entire page from top to bottom so content that only appears on scroll — lazy-loaded images, below-fold sections, infinite-feed entries — is included in the captured HTML and screenshot, then waits for the page to stop changing before capturing. This makes captures slower but complete: what Wardress compares is what a real visitor scrolls through.

<Info>
  If you upgraded Wardress from a version without auto-scrolling, the **first scan** after the update may flag below-fold content as new: baselines captured earlier simply do not contain it. This is a one-time difference that self-heals after the next rebaseline — force a re-baseline from the site detail panel to refresh immediately.
</Info>

### Consent & Cookie Banners

Captures use a fresh browser with no stored cookies, so many sites greet every capture with a first-visit consent banner — which would otherwise obscure content in the screenshot, block scrolling, and inject changing elements into the DOM. Wardress suppresses these banners two ways: before navigation it injects the well-known consent-management-platform cookies (OneTrust, Cookiebot, CookieYes, IAB TCF v2, and others), and if a banner still appears it clicks a known accept/dismiss control from a curated list before scrolling. Dismissal is best-effort — a banner Wardress cannot recognize is captured as-is, and dismissal never fails a capture.

<Info>
  If you upgraded Wardress from a version without banner dismissal, the **first scan** after the update may flag the now-missing banner elements as a change: baselines captured earlier contain the banner. This is a one-time difference that self-heals after the next rebaseline — force a re-baseline from the site detail panel to refresh immediately.
</Info>

## AI Incident Assistant

If you have configured an AI provider under **Settings → AI providers** (any cloud provider from the model catalog, a local or cloud Ollama, or a custom OpenAI-compatible endpoint) and assigned a model to the **Explanations** task, Wardress can analyze complex cryptographic and technical diff signatures and translate them into a plain-English incident summary.

<Frame>
  <img src="/screenshots/assitant.png" alt="Incident Assistant" />
</Frame>

<Info>
  The Assistant leverages active layer evidence (such as DOM tag additions, visual similarity scores, and metadata differences). To conserve API usage, summaries are cached in the database.
</Info>

## Remediation Hooks

Wardress can orchestrate automated responses when a site is flagged.

<Steps>
  <Step title="Configure Webhook">
    Define a webhook endpoint (e.g., a serverless function to enable a maintenance page or rollback a deployment).
  </Step>
  <Step title="Trigger Alert">
    When a scan exceeds the configured risk threshold, the webhook is queued.
  </Step>
  <Step title="Manual Confirmation">
    By default, all hooks require manual confirmation (`requires_manual_confirm=true`). Executions park in the confirmation queue and will not fire until explicitly approved by an operator.
  </Step>
</Steps>
